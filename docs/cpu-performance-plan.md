- 2026-09-12，x87 持续缓存（组件版本 5，以下 v3/v4 段落为历史实现）：物理栈槽现在维护 `f64` 权威值、有效位和脏位。Wasm 局部变量仍限于寄存器区域，但区域结束、普通跳转和模块返回不再自动转换回 F80。旧 helper 读取单槽时按需同步；MMX 别名访问、FXSAVE/FSAVE 和宿主存档有明确同步边界，恢复/覆盖寄存器时使旧缓存失效。FINIT 只重置标签、控制字和 TOP，保留物理槽缓存；普通 SSE 运算不触发 MMX 屏障。
  - 扩大原生区域到 1～32 条指令，增加 `FUCOM/FUCOMP/FUCOMPP/FUCOMI/FUCOMIP`、`FST/FSTP ST(i)`、`FLD1/FLDZ`、`FCHS/FABS`、`FFREE`、`FINCSTP/FDECSTP`、`FNOP`。`FRNDINT` 直接生成 Wasm nearest/floor/ceil/trunc，遵循客户机 RC，保留既有整数舍入语义。

  - **尚未做到整个 x87 都直接生成 Wasm 指令**：平方根、余数、缩放、对数、FXTRACT、条件移动、BCD、整数及 m32/m80 转换等仍有旧 helper/F80 桥接。它们只同步需要的槽，不会无条件清空整个缓存；状态保存本身仍需生成完整 F80 格式。以上是当前覆盖边界，不能用“所有 x87 已原生化”描述。

## 1. 推荐路线与目标

原始路线：**建立游戏基准 → 消除 JIT 缓存整体清空与冷启动问题 → 优化整数/内存热路径 → 按实际占比优化 SSE、x87 与资源解压 → 评估跨模块执行和 CPU Worker 架构。** CPU Worker 已实现；后续按新的游戏记录确定剩余优化优先级。

不建议先统一降低浮点精度，也不建议直接重写整个 JIT。当前代码存在比“再加一个编译优化开关”更具体的机会：JIT 表耗尽时会清空全部缓存；部分 SSE 指令经过 helper；每条 x86 内存访问仍有地址翻译与保护检查；x87 基本运算使用 SoftFloat。

用户报告的 120–180 秒加载和复杂场景低于 20 FPS 是症状。还必须分清：客户机 CPU 运算、浏览器编译与调度、磁盘读取、网络等待、图形命令处理，以及真实 GPU 执行。不能把这些时间相加后统称为“CPU 慢”。

| 场景 | 验收目标 | 说明 |
| --- | --- | --- |
| 游戏冷加载 | 中位时间下降至少 30%；争取进入 60–90 秒范围 | 后者是方向目标，取决于 CPU 在关键路径中的占比 |
| 游戏热加载 | 单独报告，至少不能退化 | 不用缓存命中掩盖冷加载成本 |
| 固定复杂场景 | 游戏帧间隔 P95 下降至少 30%，争取稳定达到 30 FPS | 必须测游戏输出，不能拿页面 rAF 频率替代 |
| 长时间运行 | 30–60 分钟内无周期性整批重新编译尖峰 | 同时记录内存、缓存淘汰和日志积压 |
| 正确性 | 存档恢复、声音音调、图形和游戏逻辑保持正确 | 性能提升不能通过少执行客户机工作获得 |

收益遵循 Amdahl 定律：`总加速比 = 1 / ((1 - p) + p / s)`。这里 p 是关键路径中被优化部分的占比，s 是这部分的加速倍数。举例：若 150 秒中 70% 是可加速的解压执行，把该部分提高 4 倍，总时间约为 71 秒；若它只占 20%，即使提高 10 倍，总体也只有约 1.22 倍。这是计算示例，不是对两款游戏的测量。

| [Cargo.toml](../Cargo.toml)、[Makefile](../Makefile) | release 已启用 `opt-level=3`、LTO；常规 Wasm 构建启用 `bulk-memory`、`multivalue`、`simd128` | “打开 O3/SIMD”不是新的整体加速方案；先确认实际加载了哪一个产物 |

| [jit_instructions.rs](../src/rust/jit_instructions.rs) 的 `instr_0F58_*_jit` 等 | ADDPS/ADDPD/ADDSS/ADDSD 等经过 SSE helper | 核心 Wasm 开了 SIMD，不代表动态生成的 JIT 已经直接生成向量指令 |
| [cpu/string.rs](../src/rust/cpu/string.rs) | REP MOVS 已有分页、对齐与重叠判断下的快速复制路径 | 先测 fallback 原因，再补缺口；不重复增加已有 memcpy 快路径 |
| [cpu/fpu.rs](../src/rust/cpu/fpu.rs)、[softfloat.rs](../src/rust/softfloat.rs) | x87 使用 F80/SoftFloat；部分超越函数已有 f64 转换路径 | 不能笼统宣称“所有浮点都在软件模拟”或“所有 x87 运算完全精确” |
| [cpu/cpu.rs](../src/rust/cpu/cpu.rs)、[main.js](../src/main.js) | `TIME_PER_FRAME=1.0` ms；浏览器的一个 Worker 分支负责唤醒计时 | 这不等于 CPU 已迁入 Worker；时间片也不是硬实时上限 |
| [graphics_journal.js](../src/browser/glbridge/graphics_journal.js) | 连续页缓冲、Worker 压缩、IndexedDB 暂存 | 仍占用内存带宽、后台 CPU 与存储；“不阻塞主线程”不等于“无开销” |

仓库的 [how-it-works.md](how-it-works.md) 可帮助理解结构，但具体决策以当前代码和 profile 为准，避免把历史描述当成现状。

## 3. P0：先建立能定位问题的基准

预计 2–4 个工作日。交付物应包括可重复的场景说明、计数器导出、浏览器 trace 和逐轮结果 CSV。

### 3.1 固定环境与负载

记录宿主 CPU/内存、系统与浏览器完整版本、供电及功耗模式、显示分辨率、客户机内存与显存、磁盘镜像版本、图形代理与 Wasm 构建哈希。确认没有 `disable_jit`，实际使用 release Wasm，未因特性检测退回 fallback；比较产物哈希和加载请求，不只看文件名。

为每款游戏固定至少四段：

1. 桌面点击程序到登录界面可交互。
2. 登录后进入固定地图/赛道，到资源加载完成且可操作。
3. 固定简单场景 60 秒。
4. 固定复杂场景 60 秒，明确角色数量、特效、镜头与移动路线。

网络登录/服务器响应单独计时，不能归入解压耗时。线上场景难以复现时使用相同的合法离线测试环境或固定测试条件，并记录波动，不把不同人数的场景当 A/B 对照。

区分三种“冷”：浏览器磁盘/HTTP 缓存、客户机文件缓存、JIT 代码缓存。每轮明确重置哪些缓存。不要直接删除用户正在使用的数据；测试使用隔离浏览器配置和镜像副本。存档可用于固定稳态场景，但不能代替程序冷启动测试。

每组先跑至少 5 轮，基线与候选版本交替执行；若结论接近噪声范围，再增加样本。性能验收使用无插桩 release 构建；profile 构建用于归因，不把它的绝对 FPS 当发布性能。

### 3.2 需要采集的指标

| 层次 | 必须记录的指标 | 能回答的问题 |
| --- | --- | --- |
| 客户机执行 | 解释执行/缓存执行的指令步数；热点 EIP、模块偏移和调用 helper 的耗时采样 | 时间花在游戏逻辑、解压、x87，还是解释执行？ |
| JIT 生命周期 | 分析、代码生成、编译等待各自耗时；缓存命中；淘汰；SMC 失效；模块大小；表槽占用 | 是否一直在重新编译，而不是稳定运行？ |
| 内存 | TLB miss、跨页、MMIO、只读页、写代码页等慢路径占比 | 瓶颈是数据处理还是保护/翻译开销？ |
| 浏览器 | 主线程长任务、JS/Wasm 栈采样、GC、Worker CPU、调度等待 | 宿主 CPU 是否被渲染或压缩抢占？ |
| I/O | 读取次数、字节数、块大小、缓存命中、等待时长 | 2–3 分钟里有多少不是 CPU 在计算？ |
| 图形 | 目标游戏 session 的 Present 间隔、命令处理耗时、shader 编译、GPU 时间 | 是客户机提交不够快，还是 GPU 处理不完？ |
| 存档日志 | 原始字节/秒、压缩吞吐、排队页数与字节数、驻留内存、IndexedDB 等待 | 是否出现后台积压或内存带宽竞争？ |

帧时间报告中位数、P95、P99、超过 50/100 ms 的次数。由游戏帧间隔定义 FPS/1% low，并写清计算方式；过滤辅助进程的 D3D9 Present。异步 I/O、GPU、Worker 时间可能重叠，分析关键路径时不能简单相加。GPU 时间查询只在特性可用且用于诊断时启用，不在每帧强制等待 `onSubmittedWorkDone()`。

已有计数器在 [profiler.rs](../src/rust/profiler.rs)，重点读取：`RUN_INTERPRETED_STEPS`、`RUN_FROM_CACHE_STEPS`、`INVALIDATE_ALL_MODULES_NO_FREE_WASM_INDICES`、各类 `SAFE_READ/WRITE_*`、`TLB_MISS`、`INDIRECT_JUMP*` 和 `CONDITION_*`。它们是事件数，不是耗时百分比。已有构建入口：

```sh
make with-profiler
# 或使用 debug.html 对应的调试产物：
make debug-with-profiler
```

`with-profiler` 会覆盖 `build/v86.wasm`。基准应在隔离 checkout/产物目录保存普通 release 与 profiler 两套产物；切回普通版本时强制重新生成，避免 make 因时间戳而继续使用插桩文件。

V8 的 Wasm 有分层编译；调试器和 Performance 录制也会影响编译层级。因此正式 FPS 与加载计时在关闭 DevTools 的条件下采集，trace 单独跑，并与目标浏览器版本匹配。[V8 编译流程说明](https://v8.dev/docs/wasm-compilation-pipeline)

## 4. P1：JIT 冷启动、缓存与整数执行

### 4.1 先消除“缓存满了全部重编译”

**启动条件：** 加载或复杂场景中全缓存失效计数增长，并与帧时间尖峰、解释执行回升重合。即使没有触发，也先保留计数，避免盲改。

建议把表槽耗尽时的整体清空改为有预算的选择性淘汰：

- 以整个 JIT 模块为淘汰单位，初版采用 CLOCK/近似 LRU，在模块入口或抽样时更新热度，避免每条指令维护链表。
- 同时限制表槽和生成代码字节预算；JS/Wasm 原生机器码的实际占用另行采样，不能仅用 Wasm 文件字节估算。
- 不淘汰正在执行或正在编译的模块；清理其页映射、入口索引和 table 引用。若没有可淘汰项，暂缓编译并继续解释执行，不强制破坏正在使用的状态。
- 为槽位引入 generation/编译任务身份检查，防止异步完成的旧编译结果写回已复用槽位。
- 写代码页、页重映射、状态恢复仍执行正确失效。缓存保留策略不能跳过 SMC 检查。

先保持接近现有内存预算验证策略收益，再对容量做小范围 A/B。增大 `WASM_TABLE_SIZE` 必须同步 Rust/JS 表约定；不建议先把 900 改成一个很大的数。

涉及文件：`src/rust/jit.rs`、`src/cpu.js`、`src/const.js`。验收：相同场景的整批重编译尖峰消失或显著减少，长时间内存有界，页面修改及恢复测试通过。

### 4.2 编译热度与模块形状

扫描候选参数，而不是一次全部放大：

| 参数 | 第一轮候选 | 注意事项 |
| --- | --- | --- |
| `JIT_THRESHOLD` | 50k、100k、200k | 当前是编译期常量；改变它需要构建候选版本，或先增加受控实验配置 |
| `MAX_PAGES` | 1、3、6 | 跨页更多可能减少退出，也可能增加编译、分支调度和内存成本 |
| `MAX_EXTRA_BASIC_BLOCKS` | 64、128、250 | 重点减少只执行一次的冷路径和巨大 dispatcher |
| 编译队列 | 先观测当前单个 compiling 状态的等待，再评估很小的有界队列 | 不能无界并行生成和编译模块 |

现有 `set_jit_config` 的索引 1、3 分别对应页数和额外块数；索引 2 是 loop safety，**不把关闭它作为性能方案**。参数实验需在干净 JIT 状态下开始。后续可按“加载阶段偏低热度阈值、稳态偏热点复用”的策略设计，但必须用可观测负载触发，不能按游戏名称硬编码时间。

### 4.3 整数 IR 与标志位活跃性

先做基本块内、再扩展到可证明的块间优化。针对真实热点加入轻量 IR/分析元数据，不要求先搭建完整 SSA 编译器。

优先顺序：

1. 标志位活跃性：去掉在读取前就被覆盖的 lazy-flags 更新，扩展已有算术后条件分支优化。
2. 常量传播、死写消除、冗余高位 mask、地址表达式合并，重点观察 8/16 位子寄存器与解压的字节读取。
3. 对真正热的整数 helper 直接生成 Wasm；特别检查位流移位、整数比较、带进位操作和乘除法，而不是按指令表全面重写。
4. 减少 helper 调用前后的状态同步，只在确定状态无外部可见性时保留局部值。

必须保留 CF/PF/AF/ZF/SF/OF、`ADC/SBB`、保留 CF 的 `INC/DEC`、移位计数为零、`PUSHF/LAHF` 等语义。DIV/IDIV 的零除与商溢出要转成正确客户机异常，不能让 Wasm trap 代替。发生 page fault 的指令不能提前提交结果；异常、块出口、helper、调试观察点需要可重建的精确 CPU 状态。

涉及文件：`analysis.rs`、`codegen.rs`、`jit_instructions.rs`、`state_flags.rs`、`gen/` 下的生成器。不要只手改自动生成的 `src/rust/gen/*`。

### 4.4 内存与 REP 热路径

对同页、普通 RAM、权限稳定的连续访问，研究复用已验证的地址翻译和范围检查，减少每次 load/store 都重复验证的开销。安全边界是基本块/受保护小段：跨页、MMIO、代码页写入、地址空间或权限变更时立即退回原路径。

REP 已有批量复制优化，应先根据慢路径统计扩展。尤其注意：**x86 的顺序重叠复制不总等价于 memmove**。LZ 类解压会边复制边引用刚写出的数据，不能直接用一次 `memory.copy` 替代所有重叠循环。需要独立验证向前/向后复制、16 位地址回绕、跨页中途 fault，以及完成部分元素后的 ECX/ESI/EDI 状态。任何向量化读取都不得为了方便而越过有效映射边界。

## 5. P2：浮点优化，先 SSE，再有条件地优化 x87

### 5.1 SSE/SSE2 直接 JIT

若 profile 显示 SSE helper 是热点，先选择常用标量算术、向量逻辑/移动，再覆盖 packed 运算。目标是在 JIT 模块里直接生成 `f32/f64` 或 `v128` 运算，减少 XMM 状态搬运与 helper 边界。

需要扩展 `wasmgen/wasm_builder.rs`、`wasm_opcodes.rs` 和对应 JIT emitter。先审计寄存器形式，再做内存形式：后者必须保留 fault、对齐和只修改低 lane 的行为。Rust helper 可能已被 LLVM 向量化，真实收益应来自跨指令保留 XMM locals、减少调用与搬运，不能假设每个 helper 内部都是最差标量代码。

Wasm SIMD 没有直接提供 x86 的所有舍入/非正规数控制；MXCSR、NaN、正负零、MIN/MAX、浮点转整数、DAZ/FTZ 都要逐项验证。优先选择语义明确的子集，其余保留兼容路径；不默认使用 relaxed SIMD 或 fast-math。[Emscripten SIMD 文档](https://emscripten.org/docs/porting/simd.html)

### 5.2 x87：先减少 SoftFloat 包装成本

2026-09-09：首批精确乘法和 2 的幂除法快路径已实现，并增加差分测试和微基准；回退开销需与快路径收益一起评估。尚未验证真实游戏收益。

只有当 F80 helper 的采样耗时显著时，才把它提升到高优先级。先优化不会改变数值语义的工作：减少 F80 载入/存储、重复格式转换、临时结构和无必要的栈/tag 处理；保持 FPU 栈、控制字、状态字和异常状态在退出点可观察。

更激进的 f64 快路径需要分成两种：

- **严格路径：** 必须证明所选操作与输入范围能得到相同结果和可见状态；证据不足就调用原 helper。例如可证明精确的小整数运算子集比任意 x87 运算更适合作为起点。
- **实验兼容模式：** 若产品允许在特定游戏内使用近似 f64 计算，可独立评估，默认关闭，明确记录配置和存档兼容性，不能称为精确 x87 优化。

不能只检查“x87 精度控制是 53 位”就把所有操作换成 f64：扩展指数范围、双重舍入、异常标志、80 位内存访问及后续指令观察仍可能不同。SoftFloat 的扩展精度与异常状态是接口的一部分。[SoftFloat 接口说明](https://www.jhauser.us/arithmetic/SoftFloat-3/doc/SoftFloat.html)

若采用可回退的推测执行，必须保存足够的输入/中间状态，并在任何客户机可见写入、异常和 helper 副作用发生前完成验证；不能先写回错误结果，再寄希望于下一条指令回退。

验证覆盖所有舍入模式、精度控制、NaN/Inf、负零、非正规数、溢出/下溢、整数转换、80 位读写、栈溢出/下溢与存档恢复。检查两款游戏实际 x87/SSE 占比，不凭游戏年代判断。

## 6. P2：压缩与解压分三条处理

### 6.1 客户机内部的游戏资源解压：默认优先通用加速

这里执行的是客户机 x86 代码，宿主 `CompressionStream` 或替换 `lib/zstd` 不会自动加速它。

先取得热点 EIP、输入/输出数据和函数边界，识别实际算法及其耗时。MapleStory 的资源容器处理、跑跑的资源加载可能还包含解密、校验、格式解析、内存分配或网络等待；本次尚未确认算法，不能预设“全是 zlib”。

通用优化重点是整数位操作、分支、小字节 load/store、重叠复制、TLB 检查、热点编译与缓存保留。建立同一份 x86 解压程序在解释器/JIT 两种模式下的 MB/s 基准，同时保留真实游戏端到端时间。

### 6.2 可选专用加速接口：在证据充分后评估

如果某个已识别的解压函数占加载关键路径的大部分时间，单纯 JIT 优化仍达不到目标，可考虑把该算法编译为宿主 Wasm，通过受控客户机代理接口调用。这是可选的半虚拟化方案，不是透明 CPU 加速。

要求明确：匹配算法版本、窗口/字典、流式状态、错误码与实际输入；完整校验输出边界；保留同步调用语义和客户机页错误语义；保存/恢复未完成状态；未知版本使用原实现。优先一次传输大块数据，计入复制与调度开销。验证正常、损坏、截断输入，输出逐字节一致；压缩端若不能做到相同码流，至少明确兼容要求并验证官方解码器可读，不能偷偷更换协议格式。

第一版优先请求级同步加速，避免跨客户机页错误的大规模直接写入。只有已独立分块的任务才并行；单个有历史依赖的解压流不能任意拆给多个 Worker。该路线不能依赖关闭程序完整性检查或绕过保护来成立。

### 6.3 宿主图形日志压缩与镜像解压

图形日志现在已在 Worker 压缩，但可能与客户机争抢 CPU/内存带宽。新增压缩 backlog 的页数、字节数和最大驻留内存指标，并用实验版开关测“完整日志”与“仅诊断性关闭日志”的开销差值；关闭日志的测试会失去相应图形存档能力，不作为正式默认配置。

若积压明显，评估有界原始页暂存、后台低优先级压缩，保存时等到所有页完整落盘/打包。磁盘、内存双预算用尽时需要显式背压或可见失败，不能丢弃历史，也不能无界排队。换更快 codec 必须版本化存档，保留当前 gzip 格式读取，并用实测权衡 CPU、文件大小、加载和回放时间。

[宿主 zstd 封装](../src/rust/zstd.rs) 只在 trace 证实相关路径占用明显时优化。算法要按用途分别评估：客户机资源解压、镜像/状态文件解压、图形日志压缩不能用同一个 MB/s 数值混为一谈。

## 7. 配套优化：加载 I/O、调度与图形 CPU 开销

**I/O：** 根据 [buffer.js](../src/buffer.js) 和 IDE 读取轨迹，检查短小请求、重复读取与缓存命中。先在测试环境比较本地预加载镜像和异步分块镜像；若差异大，再做请求合并、少量顺序预读和有界块缓存。缓存键必须包含镜像身份与版本，写入和回滚要保持一致，不让预读拿到旧数据。

**调度：** 测实际执行时间片和宿主唤醒等待。候选为 1/2/4 ms 或有截止时间的自适应预算，分别测试加载、稳态、输入延迟和音频 underrun。增加时间片可能提高吞吐却降低流畅度；不能关闭硬件计时、IRQ 检查或 loop safety 来换成绩。

**CPU Worker（已实现）：** CPU 和紧耦合设备位于专用 Worker，DOM 和 WebGPU 图形执行位于主线程，AudioWorklet 使用直接消息通道。已处理图形背压、暂停/恢复屏障和旧代次异步回复。客户机 RAM 由 Worker 独占，当前未使用 SharedArrayBuffer。用户反馈音频卡顿消失、FPS 无明显增幅；后续优化应继续针对实际 CPU 执行和图形瓶颈。

**图形：** 若复杂场景的主线程 profile 落在 D3D9 解码、shader 编译、资源创建或 GC，先优化这些地方。若 GPU 时间占主导，优化客户机整数不会直接恢复目标 FPS。沿用已有图形性能计数，按游戏 session 检查每帧提交、pipeline/buffer 创建和同步读回，不凭整页 CPU 使用率归因。

## 8. P3：跨模块执行与持久编译缓存

仅在前几阶段的 profile 仍显示明显的模块退出、dispatcher 或反复冷编译成本时投入。

### 8.1 热出口链接与块融合

先在同一模块内融合热点直连块；再评估有界的跨模块 table 调用/尾调用。缓存目标必须校验代码页 generation、地址空间/映射与执行状态，失效时走通用调度器。不能在客户机无限循环上积累宿主调用栈，也不能跳过指令预算和中断检查。

V8 对 Wasm 间接调用的优化仍在演进，具体收益取决于目标浏览器和生成形状。因此尾调用/间接调用链接必须用独立原型对比，不能承诺天然比当前 dispatcher 快。[V8 间接调用优化](https://v8.dev/blog/wasm-speculative-optimizations)、[Wasm 尾调用说明](https://v8.dev/blog/wasm-tail-call)

### 8.2 持久缓存只缓存可验证的代码，不缓存裸入口

先考虑缓存 x86 代码分析结果或生成的 Wasm 字节，再评估浏览器特定的 compiled module 保存能力。键至少包含代码页内容、映射/重定位假设、执行模式、CPU 特性、JIT 版本、导入 ABI、所需 Wasm 特性及浮点模式。加载时重新验证，代码变化、SMC、版本变化和 restore 后失效。

动态生成的 Wasm 字节不应假设自动享有与同 URL streaming 模块相同的浏览器磁盘代码缓存。持久命中带来的“热加载”成绩必须与首次编译成绩分列。[V8 代码缓存说明](https://v8.dev/blog/wasm-code-caching)

## 9. 实施顺序、投入与停止条件

以下是熟悉仓库的一名工程师的粗估工作量，包含针对性测试，不是承诺工期；发现兼容性问题后重新估算。各项不是简单相加，也不建议全部同时启动。

| 阶段 | 投入范围 | 交付 | 进入下一步的条件 |
| --- | --- | --- | --- |
| P0 基准与归因 | 2–4 天 | 游戏场景、采样、计数器、结果表 | 明确加载与低帧各自前几名瓶颈 |
| P1a 缓存淘汰与冷启动参数 | 5–10 天 | 有界淘汰、异步安全、参数 A/B | 消除已观测的重编译尖峰，或证明此处不是瓶颈 |
| P1b 整数 flags/内存热路径 | 2–4 周 | 小范围 IR、差分测试、真实热点加速 | 至少一项游戏指标稳定改善，不能只赢微基准 |
| P2a SSE 直接生成 | 1–3 周起 | 高频指令子集与精确测试 | helper 热点占比足够且语义验证通过 |
| P2b x87 严格优化 | 2–6 周起 | 包装优化与受限精确快路径 | SoftFloat 实际占用足够，精度回归为零 |
| P2c 单个解压算法专用接口 | 1–3 周原型，集成另估 | 版本限定、数据验证、同步接口 | 通用优化不足，且该算法确实主导关键路径 |
| P3 链接/持久缓存 | 分别立项，通常数周以上 | 架构原型和完整生命周期测试；CPU Worker 已完成 | 有明确量化瓶颈，预计收益足以覆盖维护成本 |

第一批建议拆成三个可独立评审的 PR：

1. `perf: add game workload and JIT lifecycle metrics`：只增加诊断和可重复场景，默认关闭昂贵采样。
2. `jit: evict cold modules without flushing the whole cache`：内存有界、槽位 generation、SMC/restore 回归。
3. `jit: optimize measured integer or SSE hotspots`：依据 profile 二选一，避免把多个收益来源混在一起。

每项必须有单独开关/可回退提交。若只在一个合成循环有效、真实场景不改善，暂停扩大实现；若另一个目标游戏出现可重复的超过 5% 性能下降，或声音/图形/存档/数值错误，先修复再推进。收益没有超过测量噪声的参数不发布为默认值。

## 10. 正确性与发布验收

按改动运行对应测试，而不是每次都无差别重跑所有镜像。现有入口包括：

```sh
make rust-test
make nasmtests nasmtests-force-jit
make jitpagingtests
make test-glbridge
```

涉及广泛 CPU 语义时扩展到 kvm-unit、QEMU 对照和系统启动测试；部分入口需要相应镜像、编译器或测试资源，执行前核实环境。

新增针对性测试要求：

- 整数/JIT：解释器与 JIT 差分，比较定义明确的寄存器、flags、内存和异常；不能依赖 x86 未定义标志位一致。用硬件或独立参考补足“双方共享 helper 错误”的盲区。
- 内存：跨页、MMIO、只读页、SMC、CR3/权限切换、地址回绕、REP 重叠及中途 fault。
- 编译缓存：容量耗尽、淘汰后返回、异步完成与 reset/restore 交错，长时间运行内存有界。
- 浮点：SoftFloat/参考实现差分与边界数据；宿主 x86 测试需要明确匹配的舍入和控制状态。
- 压缩/解压：真实资源样本、错误输入、输出校验，流式/字典边界与存档恢复。
- 游戏：两款主目标的加载与固定复杂场景；Warcraft III 回归；同实例/新实例存档恢复，恢复时无历史画面播放，声音音调正常。

后续测试结论统一记录在本文件，原始数据放在不提交的 `build/perf-results/`，每行至少包含：

```text
commit, wasm_hash, browser, host, game_version, scenario, cache_state,
run_id, load_ms, frame_median_ms, frame_p95_ms, frame_p99_ms,
interpreted_steps, jit_steps, jit_full_flushes, compile_ms,
io_wait_ms, host_peak_memory, journal_backlog_peak_bytes, correctness
```

MIPS 可辅助发现执行量变化，但不能单独作为“更快”的证据：JIT warmup、REP 计数、休眠、忙等和不同代码路径都可能改变它。最终以完成相同工作所需的墙钟时间、游戏帧间隔及正确性验收。
