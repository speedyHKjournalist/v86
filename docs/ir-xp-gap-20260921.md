# XP IR 与 legacy 的剩余差距复核（2026-09-21）

源码起点：`b8885b9b`。用户给出的 44.23 → 42.10 秒、35.08 → 36.85 mIPS、
15.54 → 18.37 指令/激活来自 `build/ir-next-xp-summary.json`，不是本次修改的跑分。
该轮 legacy 为 22.907 秒 / 92.486 mIPS：IR 吞吐是 legacy 的 **39.85%**，
即低 **60.15%**；启动显示里程碑耗时多 **83.8%**。这里的“40%”是吞吐比。
XP 轮询和客户机时钟会改变退休工作量，不能把这个比值当成同一固定程序的速度比。

## 为什么上一轮只有约 5% 改善

1. **普通区域边界仍非常频繁。** 原数据的激活密度从 51,714 降至 43,408 次/百万
   退休指令，但 IR 的链接仍循环调用 `execute_one`，做后继查找、准入、映射检查、
   取指、Wasm 调用和结束统计；普通出口也仍物化 CPU 状态。legacy 的同模块控制流
   保留 locals，跨模块使用 `tlb_code/state_table` 查找。两者都叫 JIT，并不意味着
   每条跨区域边的成本相同。
2. **helper 继续执行把检查搬进区域，没有消除检查。** 原三轮入口完整检查中位数
   下降到 33,149 次/百万，但 observer 完整检查增加到 6,193 次/百万。每轮合计再取
   中位数为 39,393，优化前是 38,820，反而增加 1.5%。这不是检查耗时或比较字节数；
   不能据此宣称验证次数也同比下降了 16%。
3. **约五分之一指令仍解释执行，在线编译仍贵。** 旧的 hot-ring BTree 索引、
   单块分配、直线 lifting、后继缓存、helper IRQ 判定已经修过。剩余问题不能继续
   归因于这些已经消除的旧热点，也不能一概归为 x86 指令不支持。

## 当前源码重新采样

在同一镜像上串行运行当前 IR 与 legacy，关闭 IR 诊断、性能记录和 capture 导出，
仅开启 Node/V8 CPU sampling。这里用于归因，正式性能比较另做无采样配对。
原核心保存在 `build/ir-gap-baseline/v86-ir-runtime.wasm`，SHA-256：
`0431173ab68f11fe6770b6581daaccdb6fe851ab3ea0d34eab0f847789f32456`。

| 栈分类的采样秒数 | 当前 IR（修改前） | legacy |
| --- | ---: | ---: |
| IR 准入/分派 | 6.440 | 0.793 |
| 解释器 | 6.008 | 2.778 |
| 编译器 | 5.137 | 0.495 |
| 生成代码及其 helper | 5.960 | 6.794 |
| IR 调度 | 1.276 | 0.271 |
| idle | 5.242 | 4.714 |
| 总采样区间（含其他 core/host/GC） | 34.989 | 18.963 |

legacy 也使用带 IR 实验功能的同一核心，因此会支付少量空 IR dispatch/scheduler
检查。表中按整轮采样归类，既不是 OS 独占 CPU 时间，也不是等退休工作量比较。
本轮 IR/legacy 里程碑为 34.865/18.730 秒，退休数约 15.68/21.65 亿；不得与之前
会话的 42.10/22.91 秒直接相减来声称优化收益。

IR 编译栈约是 legacy 的 10.4 倍，但 IR 发布 2,401 个区域，legacy 请求 277 个
模块，单位和区域大小不同，**不是单次编译慢十倍**。IR 解释器工作占总退休数约
20.2%；缓存 IR 激活约 8,172 万次，入口完整检查约 6,066 万次，加上 observer
约 977 万次。生成整数代码并不能解释这些额外调度和编译工作。

可定位的叶函数采样：`execute_one` 2.833 秒、`cached_match` 2.246 秒、
`successor_target` 1.095 秒、`ir_cache_collect` 0.400 秒。HIR verifier 的包含
子调用采样约 1.187 秒，占 IR 编译采样约 23.1%；编译调用栈中的分配器叶采样
约 0.796 秒，二者可能重叠，不能相加。

修正了 `cpu_profile_report.mjs` 的归类缺陷：无诊断版本会把 `jit_run_interpreted`
内联到 `main_loop`，原脚本只认函数包装层，误报解释器仅 0.043%。现在也识别
`gen::interpreter*::run` 及其子调用，并单列 legacy compiler。无可识别栈帧的
内联工作仍留在 other core，不把不可识别时间强行分摊。

另跑周期 16 的独立诊断，守恒检查通过：

- 普通退出 5,426 万次，占激活 **94.96%**，普通退出平均 **15.97 条指令**。
- 预算退出仅 3.28%；扩大执行预算不能消除绝大部分普通边界。
- 缓存 IR 覆盖 **80.26%**。缺失 3,240 万次，其中 unseen 1,424 万、heating
  801 万、ready 862 万、pending 153 万、failed 76。这里是缺失访问次数，
  不是独立 PC 数量；unseen 表示当前有界热度表没有记录，不代表从未执行。
  ready 表示达到编译热度，pending 包含已编译队列/待安装。
  大量缺失访问已经达到热度门槛，不能把缺失都称为“不支持指令”。
- Tier 1 发现到发布平均约 64.2 ms、最大 2.74 秒；Tier 2 平均约 139.2 ms。
  该计时含执行、排队与安装，不能额外加到总启动时间上。
- 编译 pipeline 全调用计时 6.197 秒，lowering 2.545 秒，其中 HIR allocation
  1.435 秒；machine allocation 0.651 秒。多块分配及 Tier 2 重编仍有成本。

原始证据使用 `build/ir-gap-{current,legacy}.cpuprofile`、
`build/ir-gap-{current,legacy}-profile{,-summary}.json[l]` 和
`build/ir-gap-current-diagnostic{,-summary}.json[l]`。

## 本次实现

- `runtime/snapshot.rs`：单映射源码直接检查页内长度、线性页、物理地址和真实
  字节，避免通用分片循环。当前映射检查仍最先执行，多页保留原路径；发布身份、
  代际、取指后复核、observer、SMC 和回收协议保持原样。不增加 owner 元数据。
- `verify.rs` / `state.rs`：复用指令签名类型缓冲；恢复状态采用无分配迭代；
  去掉 effect-root/XMM 签名的临时 Vec。保留全部验证、错误顺序及恢复操作数顺序。
- `performance/boundaries.mjs`：新增预热固定工作量边界基准。连续循环、同页跳转、
  跨页短区域执行相同整数运算；同页/跨页组退休指令数相同，独立 oracle 验证寄存器、
  FLAGS、最终 IP、结果内存及保护字。默认关闭融合以隔离边界成本，不冒充 XP 全负载。

这两处优化针对已测热点，但没有扩大跨区域的寄存器保留范围，也没有解决发布等待。
能否追平 legacy，必须由关闭诊断的 XP 配对数据判定。

### 已撤下的预计算候选

先试过在每个 cache owner 增加预计算分片元数据。与 verifier 优化组合后，
关闭诊断的三轮 IR/基线时间分别为 35.043/34.238、33.875/33.610、
33.715/32.288 秒，三组均更慢；中位时间增加 0.8%，中位吞吐下降 1.2%。
候选没有获得可确认的净收益，已经撤下；不能将代码改动本身视作性能改善。
额外 Vec/Record 字段与间接访问是可能的抵消成本，尚无单独归因实验。
记录为 `build/ir-gap-xp-summary.json`，候选核心和 patch 分别保留在
`build/ir-gap-prepared-candidate.wasm` / `build/ir-gap-prepared-snapshot.patch`。

### 相同输入的编译验证

从既有 XP 不可变 capture 语料回放 2,540 个编译输入，原生二进制串行交替各三次。
基线为上一轮保存的 `build/ir-next-baseline/replay-optimized-native`，包含原有块级
活跃性优化；本次只改变 verifier 的分配/遍历。每轮读取和解析输入不计入计时。

| 编译阶段，中位数 | 基线 | 本次 |
| --- | ---: | ---: |
| passes（含 HIR 校验） | 2097.995 ms | 1461.083 ms |
| lowering | 2228.820 ms | 2174.378 ms |
| 完整编译 | 13153.795 ms | 12488.520 ms |

完整编译时间下降 **5.1%**，passes 阶段下降 **30.4%**。两版各三轮均 2,540 成功、
0 失败；生成代码均 37,122,456 字节、滚动校验 `b4ed1a18b3c1bd95`，说明该语料
代码产物未变。这是含 debug 检查的原生编译器测量，不是浏览器/XP 的提速比。
语料只含成功发布的输入，不覆盖失败编译和排队。原始输出：
`build/ir-gap-replay-paired.log`。
