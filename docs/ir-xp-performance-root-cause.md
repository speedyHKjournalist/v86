# XP 下 IR 性能退化的原因复核（2026-09-20）

结论：当前 IR 的主要问题是执行区域短、区域边界昂贵、在线编译覆盖不足，
而非已经优化过的整数指令本体慢了两倍。IR 提供跨指令优化的条件；能否提速，
还取决于连续执行范围、状态同步、编译成本及实际命中率。目前这些成本抵消了收益。

这份分析记录修改前源码和已有原始 JSONL/CPU profile，重算统计及守恒关系。
下列原始性能数据来自 `ir-sync` 验收轮；后续实现和新跑分见
[四步实施与验证记录](ir-xp-performance-implementation.md)。

## 1. 三个指标衡量的不是同一件事

数据：`build/ir-sync-xp-summary.json`、`build/ir-sync-fixed-work.jsonl`。

- XP 达到首次 800×600×32 的中位时间为 33.717 / 19.251 秒，IR 耗时为
  legacy 的 1.751 倍。这是显示模式里程碑，不是完整桌面就绪。
- 到达里程碑的中位退休指令数约为 IR 15.41 亿、legacy 21.19 亿。客户机时钟、
  等待及轮询使执行工作量不同。45.688 / 110.088 = 0.415 的吞吐比不能直接
  当作相同代码、相同工作量下的速度比；它与明显的启动退化并不矛盾。
- 固定工作量测试会先进行 20 次预热，IR 必须到 Tier 2；计时段执行相同指令数，
  并检查最终架构状态及缓存 IR 覆盖。它不包含 XP 主要经历的冷编译过程。

| 固定工作量 | IR / legacy 吞吐 |
| --- | ---: |
| 整数 | 0.942 |
| RAM RMW | 0.917 |
| 间接区域 | 1.695 |
| SSE 寄存器 | 0.982 |

几何平均 1.095 的优势主要由间接区域一项贡献；其余三项尚未超过 legacy。
门槛通过不表示普遍提速。这四个极小热循环也不代表分页、中断、端口轮询和
多入口工作集。测试实现见 `tests/ir/performance/fixed_work.mjs`。

## 2. 第一瓶颈：短区域频繁经过完整运行时入口

关闭诊断的三轮 IR 日志显示：

- 缓存 IR 执行占退休指令约 77.0%～78.0%。
- 共约 8036～8183 万次 IR 激活，平均每次只有 14.74～14.90 条指令。
- 共约 5678～6180 万次完整准入校验。

这些计数取自各轮 `result`，停止时间略晚于里程碑，不冒充精确里程碑计数。

`src/rust/ir/runtime/cache.rs:715` 的链接是循环调用 `execute_one`，每个后继
仍需查目标、检查入口上下文/代际/映射、必要时比较源代码、执行取指与发布者
检查，然后调用 Wasm，返回后更新统计、热度和退出信息。
`src/rust/ir/backend/wasm.rs:105` 的普通出口先执行状态物化，再请求链接并返回。
因此现有跨区域链接不等价于在一个 SSA 区域内持续携带寄存器值。

`src/rust/ir/runtime/snapshot.rs:98` 的完整检查确实逐片比较当前 RAM 字节与
编译快照，融合区域还要检查其他源快照。快速检查已经启用，但证书不能跨越
CPU batch、解释器及可观察 host 的 helper，见 `runtime/entry.rs:26`。
这解释了为何有 fast entry 仍有数千万次完整检查。

独立诊断轮的 8130 万次退出中：

| 退出类别 | 次数 | 占激活比例 |
| --- | ---: | ---: |
| 普通控制流 | 6401 万 | 78.7% |
| helper invalidated | 1014 万 | 12.5% |
| interrupt shadow | 512 万 | 6.3% |
| 执行预算耗尽 | 146 万 | 1.8% |

普通出口对应平均约 13.03 条指令。首要方向应是减少普通控制流边界以及每次
边界的成本；单纯把 execution budget 从 256 调大，无法消除这些普通出口。
这里的预算退出和编译器的 fusion budget rejection 是两种不同的预算。

## 3. 形成区域的范围小，系统指令又进一步截断执行

`runtime/region.rs:20` 的默认 Tier 1 最多 192 字节/32 条指令，Tier 2 最多
384 字节/96 条指令；直接调用停止该扫描，窗口之外的控制流成为外部出口。
融合最多四个源；三/四源含未审计 observer 的情况仍被拒绝，见
`runtime/compile.rs:291`。已有可用融合不是缺失，但不足以覆盖真实执行路径。

对照 legacy：`src/rust/jit.rs:610` 按页和多入口形成模块，当前策略上限为
Tier 1 一页、32 位 Tier 2 六页；`jit.rs:1448` 已将 GPR 放入 Wasm locals，
同模块内有结构化控制流。跨模块链接同样可能写回，但其后继查找直接利用
`tlb_code`、状态标记和 `state_table`，见 `cpu/cpu.rs:3449`，没有 IR 当前这套
源快照逐字节准入路径。上限不等于每个实际模块都覆盖这些页。

诊断轮还记录端口读取退出约 490 万次、CPU control 约 477 万次，以及上述
interrupt-shadow 退出。RDTSC/CPUID 等在 `frontend/cpu_info.rs` 走终端 helper；
`runtime/cpu_info.rs` 成功返回也使用 `Outcome::Invalidated`，不能连续执行。
CPU control 是合并类别，当前计数不能证明其中多少属于 RDTSC。

这些边界会同时打断 SSA 状态保留、迫使物化/恢复，并使准入证书失效。
此前无限制扩大含 helper 区域出现 XP 行为退化，故不能以删除保护来获得数字收益。
应对具体 helper 明确读取/修改状态、异常路径、host 回调及代码/映射失效协议。

## 4. 第二瓶颈：在线覆盖与热度管理的成本

约 22%～23% 的退休指令没有走缓存 IR；独立诊断守恒检查确认其为解释执行，
该轮 legacy 步数为零。成功记录中的 `unsupported_stops` 为零，所以不能把
这些解释器工作一概归因为“不支持 x86 指令”。

源码中的具体影响因素：

- `runtime/schedule.rs:200` 使用 128 项 hot ring 和 BTreeMap 索引；入口替换会
  删除旧键、插入新键。`visit` 每帧最多消耗一次编译机会，只允许一个待发布任务；
  host 发布异步完成，期间仍需执行客户机代码。
- `cpu/cpu.rs:3308` 在 IR 模式下每个解释器反向跳转或 64 条指令就返回外层，
  用来暴露热度及已发布入口；未及时编译的短循环会反复支付调度和查找成本。
- 默认缓存只有 256 个区域。三輪约 1215～1237 次淘汰，存在再预热压力。
  但已有 768 项单次实验虽减少淘汰到 550 次，启动仍约 33.2 秒、覆盖仅约
  79.8%，表明容量不是足以单独解释差距的因素。

对原始 `build/ir-sync-xp.cpuprofile` 重新沿栈分类，调度路径的 BTree 叶函数
累计采样约 2.040 秒，占调度组 3.364 秒的约 60.6%，占整轮采样约 5.3%。
这是可定位的热路径管理开销。它不证明具体替换策略的收益，仍需独立 A/B。
诊断中的 hotspot replacement 是诊断表冲突计数，不能当作 hot ring 淘汰数。

## 5. 编译成本显著，但不是唯一主因

独立 profile 的分组如下，分母包含 idle；这是采样墙钟区间而非独占 OS CPU 时间：

| 分组 | 采样占比 |
| --- | ---: |
| IR 准入与分派 | 22.6% |
| 解释器 | 18.9% |
| IR 编译器 | 13.3% |
| 已生成代码及其调用的 helper | 12.3% |
| IR 调度 | 8.8% |
| idle | 12.4% |
| 其他 core、host/device、GC 合计 | 11.8% |

例如同一配对轮停止时，IR 发布 2423 个 Tier 1/2 区域，legacy 发起 291 次模块
编译请求。计数单位及区域大小不同，不能据此说单次 IR 编译慢八倍；它说明 IR
存在大量小单元的构建与发布工作。Tier 1 仍需 HIR、lowering、分配与必要校验。

全调用编译计时显示 lowering 合计 2.466 秒、最长 47.81 ms；机器优化合计
0.573 秒、最长 5.47 ms。本轮未复现旧的长停顿。发布延迟累计 9.458 秒与
执行重叠，不能直接叠加到启动时间。

这份 profile 带周期 16 的诊断，整轮约 38.1 秒，有观测扰动。更细的
`estimated_ms` 外推总和失真，不能用它分摊验收轮的 33.7 秒。只作量级推演：
若其他行为固定，仅把“生成代码及 helper”这一组加速两倍，按该采样构成
整体只约快 6.5%；即便把编译器组完全消除，整体也只约快 15.3%。实际改造
会改变工作量和分派次数，这些不是可承诺的优化收益。

## 6. 为什么“有 IR”没有自动产生大幅加速

legacy 本来就是 x86 到 Wasm 的 JIT，已有寄存器 locals、控制流组织和快速 RAM
路径。IR 与它最终都执行 Wasm，增加 HIR/MIR 不会自动减少客户机指令对应的
机器工作；它还增加了构建、优化和验证成本。

IR 的潜力在于更大连续范围内删冗余计算、FLAGS/状态写回、内存检查和访存，
以及跨基本块优化。当前 XP 平均约十五条指令就离开区域，许多收益被边界抵消。
固定间接区域测试 1.695 倍说明合适路径已经受益，但没有证明一般工作负载
能获得相同收益。默认优化级别已为 2，无禁用 pass，不能归因为忘记开启优化。

## 7. 建议的实施优先级与验证指标

1. 优先改普通边的执行和区域组织：对高频已知后继建立可失效的快速链接，
   提高多入口共享、非连续热路径覆盖和连续携带状态的范围。保持冷入口用于
   host 回调、映射改变和异常恢复。用每百万退休指令的激活数、完整检查数衡量。
2. 把热度记录改为更便宜、少分配的结构，改进热点保留与候选选择；记录入口
   首次发现到可执行发布的延迟、未命中原因及每阶段 IR 覆盖。不能仅降低阈值，
   否则可能加重冷编译和淘汰。
3. 按热点分别处理端口读取、时钟/control helper 与 STI shadow 的选择性同步
   和续执行契约；先细分 CPU control 计数，再决定具体优先级。保留故障、
   原始 host RAM 写入、SMC、映射和中断可见时序的差分验证。
4. 降低每个 Tier 1 单元的构建/发布成本，提高共享 capture/多入口产物的复用。
   再按剩余 profile 优化状态同步、FLAGS、RAM 和 SIMD 代码质量。

每步使用同镜像交替配对、关闭观测的 XP 里程碑验收，并单独检查暖态固定工作量
及精确状态。诊断轮用于解释变化，不能替代验收轮。当前证据支持上述优先级，
不能支持“某一项修改必定达到 legacy”或“IR 必然大幅提速”的结论。
